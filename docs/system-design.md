# 小说转剧本工具：系统设计收束

## 设计结论

系统采用“完整理解 + 结构化记忆 + 局部生成 + 全局审稿”的分阶段架构。

第一版不把完整小说一次性塞进模型生成剧本，也不只依赖章节摘要。系统必须先完整阅读小说，并把阅读结果沉淀为可校验、可复用的故事档案；随后按场景检索相关原文和故事档案生成 YAML 剧本；最后通过一致性审稿器检查伏笔、人物弧光、章节覆盖和来源引用。

## 核心目标

1. 支持 3 个章节以上小说文本。
2. 输出结构化 `screenplay.yaml` 剧本初稿。
3. 降低长上下文导致的遗漏、幻觉和前后不一致。
4. 保留来源追踪，让作者能核对每场戏来自哪些章节。
5. 把“精彩程度”拆成可检查的戏剧指标，而不是承诺自动产出终稿。

## 总体流程

```text
小说输入
  -> 章节解析
  -> 完整阅读与章节理解
  -> 全局故事档案生成
  -> 情节图与伏笔表生成
  -> 改编大纲生成
  -> 逐场剧本 YAML 生成
  -> Schema 校验
  -> 全局一致性审稿
  -> 问题场景修复
  -> 输出 screenplay.yaml
```

## 分层上下文策略

### 原文层

保存完整小说原文，但不在每次模型调用中携带全文。

原文被切分为：

- chapter：章节。
- paragraph：段落。
- span：可选的更小文本片段。

每个片段保存稳定 ID、顺序、字数和哈希，便于追踪与重跑。

### 章节理解层

每章单独抽取结构化信息：

- 章节摘要。
- 出场人物。
- 地点。
- 关键事件。
- 冲突变化。
- 时间线。
- 重要物件。
- 可改编场景候选。
- 疑似伏笔。
- 重要原文位置。

章节理解层解决局部细节问题，但不能单独作为剧本生成依据。

### 全局故事档案层

把所有章节理解结果合并为全局结构：

- `story_bible.yaml`：故事设定、主题、主线、支线。
- `characters.yaml`：统一人物表、别名、动机、弧光、人物声音。
- `locations.yaml`：统一地点表。
- `timeline.yaml`：全书时间线。
- `plot_graph.yaml`：因果情节图。
- `foreshadowing.yaml`：伏笔和回收关系。

这一层是系统的长期记忆。后续生成剧本时带全局故事档案摘要，而不是带完整小说。

### 场景生成层

生成单场戏时只加载必要上下文：

- 当前场景对应的章节摘要。
- 当前场景相关原文段落。
- 相关人物卡。
- 相关地点卡。
- 前后场景摘要。
- 该场承担的戏剧功能。
- 相关伏笔和回收要求。
- YAML Schema 约束。

这样可以兼顾局部细节和全局一致性。

## 关键中间产物

### parsed_chapters.yaml

记录章节识别结果。

```yaml
chapters:
  - id: "ch_001"
    order: 1
    title: "第一章"
    word_count: 3200
    text_hash: "sha256:..."
```

### chapter_analysis.yaml

记录每章抽取结果。

```yaml
chapter_analyses:
  - chapter_id: "ch_001"
    summary: "主角发现父亲病历缺页。"
    characters:
      - "林青"
    locations:
      - "医院档案室"
    events:
      - id: "evt_raw_001"
        summary: "林青发现病历缺页。"
    possible_setups:
      - summary: "病历第七页缺失。"
```

### story_bible.yaml

记录全局故事理解。

```yaml
story:
  logline: "主角追查一份失踪档案，逐步揭开旧案真相。"
  themes:
    - "真相"
    - "复仇"
  main_conflict: "主角追查父亲死亡真相，与掩盖真相的人对抗。"
```

### plot_graph.yaml

记录事件因果关系。

```yaml
events:
  - id: "evt_001"
    summary: "林青发现病历缺页。"
    source_chapters:
      - "ch_001"
    causes: []
    effects:
      - "evt_002"
  - id: "evt_002"
    summary: "林青调查档案管理员。"
    source_chapters:
      - "ch_002"
    causes:
      - "evt_001"
    effects: []
```

### foreshadowing.yaml

记录伏笔和回收关系。

```yaml
setups:
  - id: "setup_001"
    description: "病历第七页缺失。"
    introduced_in: "ch_001"
    status: "open"
    expected_payoff: "证明医院伪造记录。"
payoffs:
  - id: "payoff_001"
    resolves: "setup_001"
    chapter_id: "ch_008"
    description: "缺页内容揭示真相。"
```

### scene_outline.yaml

记录剧本大纲。

```yaml
scenes:
  - id: "sc_001"
    order: 1
    chapter_refs:
      - "ch_001"
    dramatic_function: "inciting_incident"
    summary: "林青在档案室发现病历缺页。"
    required_events:
      - "evt_001"
    setup_ids:
      - "setup_001"
```

### screenplay.yaml

最终交付物，遵循 `screenplay_yaml/v0.1` Schema。

## 模块边界

### 1. 输入与章节解析

职责：

- 接收 `.txt` 或 `.md` 文本。
- 自动识别章节标题。
- 校验章节数不少于 3。
- 生成章节 ID、段落 ID 和文本哈希。

输出：

- `parsed_chapters.yaml`
- 原文切片索引

### 2. 完整阅读与章节理解

职责：

- 遍历所有章节，不跳读。
- 为每章生成结构化摘要和事件抽取。
- 标记人物、地点、物件、疑似伏笔和冲突变化。

输出：

- `chapter_analysis.yaml`

### 3. 全局故事档案生成

职责：

- 合并人物别名。
- 合并地点。
- 生成故事梗概、主线、支线、主题和类型风格。
- 建立人物动机和人物弧光。

输出：

- `story_bible.yaml`
- `characters.yaml`
- `locations.yaml`
- `timeline.yaml`

### 4. 情节图与伏笔表

职责：

- 把章节事件组织成因果情节图。
- 识别伏笔、推进和回收。
- 标记关键事件是否可删、可合并、必须保留。

输出：

- `plot_graph.yaml`
- `foreshadowing.yaml`

### 5. 改编大纲生成

职责：

- 把小说事件压缩为可拍摄场景。
- 为每场戏分配戏剧功能。
- 记录场景引用的章节、事件、人物和伏笔。
- 标记删减和合并原因。

输出：

- `scene_outline.yaml`

### 6. 逐场剧本生成

职责：

- 按场景大纲逐场生成 `script` 元素。
- 把心理描写转为动作、对白、旁白或备注。
- 保留 `source_refs`。
- 输出符合 YAML Schema 的场景结构。

输出：

- 初版 `screenplay.yaml`

### 7. Schema 校验

职责：

- 校验字段完整性。
- 校验 ID 引用。
- 校验章节覆盖。
- 校验枚举值。
- 校验每个场景至少有来源章节和剧本元素。

输出：

- 校验结果。
- 可定位到字段和场景的错误列表。

### 8. 全局一致性审稿

职责：

- 检查伏笔是否遗漏或无铺垫回收。
- 检查人物动机和弧光是否断裂。
- 检查事件因果是否断裂。
- 检查冲突是否升级。
- 检查对白是否过度解释。
- 检查 AI 新增内容是否缺少来源。

输出：

- `quality_report`
- 需要修复的 scene ID 列表

### 9. 问题场景修复

职责：

- 只重跑有问题的场景。
- 修复后再次执行 Schema 校验和一致性审稿。
- 保持未受影响场景稳定。

输出：

- 最终 `screenplay.yaml`

## 如何处理超长上下文

设计原则：

1. 完整小说必须被阅读，但不作为每次生成的 prompt 常驻内容。
2. 阅读结果必须结构化落盘。
3. 生成单场戏时只检索相关原文。
4. 全局故事档案作为稳定摘要参与每次生成。
5. 所有关键输出必须带来源引用或进入风险提示。

这套机制不能保证没有任何遗漏，但比单次长上下文生成更可控，也更容易定位和修复问题。

## 如何保障前后一致性

一致性不靠一次 prompt 保证，而靠多层约束：

| 问题 | 机制 |
| --- | --- |
| 人物前后矛盾 | 统一人物表、人物弧光状态、对白风格卡 |
| 伏笔遗漏 | 伏笔-回收表、场景功能标记、全局审稿 |
| 情节断裂 | 因果情节图、关键事件保留标记 |
| 章节遗漏 | 章节覆盖报告 |
| AI 幻觉 | `source_refs`、无来源内容报警 |
| 局部生成忘记全局 | 每场生成携带故事档案摘要、前后场景摘要和相关伏笔 |

## 如何提升剧本精彩程度

系统不能承诺自动生成最终精彩剧本，但可以把“精彩”拆成可检查的剧作指标：

1. 每场戏是否有明确戏剧功能。
2. 每场戏是否发生信息变化、关系变化或权力变化。
3. 主角是否持续做选择，而不是被动接收信息。
4. 冲突是否逐步升级。
5. 伏笔是否有铺垫、推进和回收。
6. 对白是否体现人物关系和潜台词，而不是只解释剧情。
7. 场景是否有清晰进入点和离开点。
8. 高潮前是否有压力累积。

这些指标进入全局一致性审稿，作为 `quality_report` 的一部分暴露给作者。

## 第一版实现边界

### 第一版必须实现

- 章节解析和 3 章校验。
- 中间产物落盘。
- 章节级结构化理解。
- 全局故事档案。
- 场景大纲。
- 剧本 YAML 生成。
- Schema 校验。
- 基础质量报告。

### 第一版可以简化

- 情节图可以先用事件前后关系和 `causes/effects` 数组表达。
- 伏笔表可以先由模型候选识别，再由质量报告提醒人工确认。
- 一致性审稿可以先输出 warnings，不自动改写所有问题。
- 检索可以先基于章节和关键词匹配，后续再引入向量检索。

### 第一版暂不实现

- 多人协作。
- Web 编辑器。
- PDF/FDX 高保真导出。
- 视频、分镜、配音生成。
- 专业制片拆解。

## PR 拆分建议

按照单一功能 PR 推进：

1. 系统设计文档。
2. 示例小说输入和目标 YAML 样例。
3. JSON Schema 校验文件。
4. 章节解析模块。
5. 中间产物数据模型。
6. 章节理解模块。
7. 故事档案与情节图模块。
8. 场景大纲模块。
9. 剧本 YAML 生成模块。
10. 校验与质量报告模块。
11. CLI 最小可运行入口。

每个 PR 合并后主分支必须保持可运行。

## 当前架构决策

1. 使用 YAML 作为剧本初稿交付格式。
2. 使用多个中间 YAML 文件承载系统记忆。
3. 不直接把 Fountain/FDX 作为第一版主格式。
4. 完整阅读是必要阶段，但必须转为结构化故事档案。
5. 剧本生成按场景逐步完成，不一次性生成整部剧本。
6. 全局一致性通过审稿器和质量报告暴露，不隐藏风险。
